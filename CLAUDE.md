# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Marketing site + booking flow for **haloe**, a hijama/cupping & massage wellness business in Manchester serving women and men. (The booking flow no longer collects gender or surfaces a chaperone requirement — Halima now handles that in person with clients; `chaperone-policy.html` was removed in Sep 2026, don't reintroduce a link to it.) Everything lives under `website-and-booking/`. There is no build step, framework, package manager, or test suite — the site is hand-written static HTML with inline `<style>` and inline `<script>`, plus a handful of Cloudflare Pages Functions and a Supabase (Postgres) database. (D1 was used for booking slot reservation until Sep 2026 — see the migration note under Slot reservation below. It's no longer used anywhere in this codebase.)

**Service model: Weekly Clinic Day: Tuesdays at Milton Hall, 244 Deansgate (Remedy Lounge), full day. Mobile visits across Greater Manchester on other days.** (see `CLINIC_VENUE_NAME`/`CLINIC_WEEKDAY`/etc. constants in `book.html`, `index.html` and the Functions — `CLINIC_START_DATE` is `'2026-10-06'`, the first bookable Tuesday, confirmed by Halima after her venue viewing; before this constant was set, the calendar showed no bookable clinic dates at all rather than defaulting to the next Tuesday, so if it's ever unset again expect that same fail-closed behaviour, not an error). The booking flow has a **Where step** (clinic / mobile / online) after the treatment and before date & time. **All bookings — clinic and mobile — are paid in full at checkout. There is no deposit option; do not reintroduce a deposit path.** Clinic bookings have no travel fee and no client address (just the venue address and a check-in note); mobile bookings keep the existing calendar and address fields, plus a postcode-driven, zone-based travel fee (see Travel cost below). Do not remove the Where step, and do not add any further clinic locations without confirming with Halima first.

**Cancellation policy (all bookings):** "Free reschedule or full refund up to 48 hours before your session. Inside 48 hours, sessions are non-refundable but can be moved once. No-shows are charged in full." This replaced the old £25-deposit cancellation wording — keep it identical everywhere it appears (`book.html`, `index.html`, `booking-confirmed.html`, `before-your-session.html`, the Stripe checkout description, and the confirmation emails).

**Travel cost (mobile bookings only — Oct 2026, distance bands from the brand doc of 18 Oct; replaced the Sep 2026 postcode zones):** priced by straight-line miles from Halima's start point (`TRAVEL_ORIGIN_POSTCODE` = `M3 7FJ`, Salford) × `ROAD_FACTOR` (1.25, approximates road miles), charged online as its own Stripe line item. Bands: up to 4 mi £20 (zone `A`), 4–8 £35 (`B`), 8–12 £50 (`C`), 12–16 £70 (`D`); beyond 16 mi there is no fixed fee — zone `Q`, a £0 "confirmed by WhatsApp" travel line, flagged in Halima's email so she quotes before the session. **The bands live ONLY in `functions/_travel.js`.** Postcodes are turned into coordinates at runtime with postcodes.io (free, no key); if that lookup is unreachable the booking is not blocked, it falls to zone `Q`. `book.html` asks `GET /travel-quote?postcode=` (`functions/travel-quote.js`) for the preview and never holds the bands; its only mirrored figure is `TRAVEL_MIN_PENCE` (£20) for "Travel fee from £20" — keep it equal to the first band. **Travel is never discounted** (one exception: a discount code row with `waive_travel = true` — `NESSA-FREE`, whose travel Halima covers — zeroes the travel line; `validateDiscountCode()` reads it fail-safe so the column can be added at any time, `supabase-waive-travel.sql`) — `create-checkout.js` computes the treatment amount (and applies any discount code to it) before travel is computed or added anywhere. The public copy — "Home visits: travel from £20, set by distance and shown before you pay. Or come to our Tuesday clinic on Deansgate — no travel fee." — appears in `book.html` (Step 1) and `index.html` (hidden widget); keep it identical. Tests: `node website-and-booking/tools/test-travel.mjs`. `booking-confirmed.html`'s "Halima will be in touch" copy is dynamic (clinic / priced / zone `Q`).

**Multi-treatment bookings (Oct 2026):** a client can select several treatments in `book.html` (`state.cart`, `toggleService()`); they're done back to back in ONE slot, sized to the summed durations, charged as ONE treatment Stripe line (price = sum, the site offer or a code applies to the sum, travel still separate and never discounted). The client posts `treatments: [{name, category}]`; `create-checkout.js`/`apply-discount.js` resolve it with `resolveCart()` in `_services.js` and never trust client prices/durations (old single `treatmentName`/`treatmentCategory` bodies still work). A package can't be combined with anything else. The booking row keeps the joined display name in `treatment` (`A + B`) and the full list in the nullable `bookings.treatments` jsonb column (null for single-treatment/old rows); the webhook and emails split `metadata[treatmentName]` on `' + '`. **Run the `treatments` migration in `supabase-bookings-schema.sql` before deploying** — `listBookings()` selects that column. **Turnaround buffer (Oct 2026):** every booking, clinic and mobile, blocks its treatment length **plus `TURNAROUND_MIN` (15 min, `functions/_slots.js`)**. `generateSlots()` adds it to the candidate slot, and `create-checkout.js` stores `end_min = start + length + 15` — so `bookings.end_min` means "blocked until", not "treatment ends", and `reserve_slot` needed no change. The client only ever sees the real length (summary, emails, admin); `book.html` sends the real duration and the server adds the gap, so there's no mirrored constant in the browser. The calendar buffer itself is separate from the **Milton Hall closing rule** (below), which has its own tidy-up setting. Older bookings made before this have no buffer. Packages are 75 min on both client (`sessionMin`) and server (`min`); `tools/test-slots.js` fails if any client/server duration drifts. There is no travel *time* in availability (only a travel fee).

**Life coaching (Oct 2026, from the brand doc):** a fifth category `coaching` in `services-data.js` / `functions/_services.js` — Life Coaching Session £50 (60 min) and Six-Session Coaching Package £250 (both 20% off until 30 Apr 2027: £40 / £200) (books the first 60-min session). **Places:** Milton Hall (Tuesdays, closing rule applies) or a third Where option, **`virtual`** ("Online", Mon–Sat 10:00–20:00 — it reuses the mobile hours table and calendar, no address, no travel). Coaching can also be added to a **home visit** (Oct 2026; the travel fee applies as usual); online is coaching-only. **A single Life Coaching Session can be combined with other treatments at Milton Hall (Oct 2026, one slot, durations and prices add up like any multi-treatment booking)**; only packages (`SOLO_CATEGORIES`, plus the Six-Session Coaching Package via `SOLO_NAMES`/`isSolo()` in `_services.js`, mirrored in `book.html`) are booked on their own. Coaching + another treatment is refused online by `cartFitsLocation()` (online is coaching-only). Enforced server-side by `cartFitsLocation()` (`400 treatment_location_mismatch`) and mirrored in `book.html` (`categoryAllowedAt()` hides tabs and prunes the cart). `bookings.location` is plain text so `'virtual'` needed no migration. **Video link:** `functions/_video.js` creates one Zoom meeting per online booking inside `notifyBooking()` and puts the join URL in the client email and Halima's email/WhatsApp; it needs Cloudflare secrets `ZOOM_ACCOUNT_ID`/`ZOOM_CLIENT_ID`/`ZOOM_CLIENT_SECRET` (Zoom Server-to-Server OAuth app, scope `meeting:write:meeting:admin`) and **without them the emails say Halima will send the link on WhatsApp**. The link is not stored on the booking row. The brand doc said coaching needs a recognised certification before it launches publicly; **Halima confirmed on 20 Oct 2026 that coaching is ready**, so it can be promoted. The homepage widget (`index.html`, hidden) has no coaching.

## Brand & positioning

- **Audience.** haloe serves both women and men. Two front doors into the business: **women's cycle/hormone health**, and **athletic recovery** (the POD Football collaboration — see Collaborator codes below). Neither front door is the whole business; treat both as entry points into the same clinic, not separate offerings.
- **Register: excellence.** Quiet, private, discreet — a Portland Hospital feel, not a spa or a salon. Never name a client, even anonymised or as a composite ("a client told me…"). Never promise an outcome. This governs tone on the site, in emails, and in social copy alike.
- **Language rules (compliance — see also the Compliance section below, which this reinforces).** Symptoms only, never condition names. Never claim a cure. Prefer "supports recovery" / "many clients notice" over any claim of effect on a named condition or a guaranteed result.
- **Clinic.** Room 4, Milton Hall (the room number is internal — never shown to clients; `venue-copy.js` gives address and concierge only), 244 Deansgate, Manchester (`CLINIC_VENUE_ADDRESS` in the Functions/pages). Tuesdays from 6 Oct 2026. The Remedy Lounge Ltd contract for the room runs from 1 Oct 2026.
- **Booking.** haloe.health/book — the only path that takes payment (see `book.html` below).
- **Discount codes** (full mechanics in the Conventions section further down):
  - `GUEST-YASMZEE` / `GUEST-DB` / `GUEST-POD` — private collaborator gift codes (renamed from `HALOE-NAME` on 29 Sep 2026 so the free code reads as a personal invitation, apart from the HALOE20 family), 100% off, locked to that collaborator's email, one use each.
  - `YASMZEE25` / `DB25` / `POD25` — collaborator audience codes, 25% off, first-time clients only.
  - POD Football prize codes are **minted per winner** (`POD-GOTW-W40`, `POD-POTM-OCT`) — single-use, 100% off, type `competition`, tagged to POD Football — with `node website-and-booking/tools/mint-pod-code.mjs <GOTW|POTM> <label> [winner-email]`. The shared `POD-GOTW`/`POD-POTM` codes are retired (`active=false`). Every 5 bookings on a `NAME25` code earns that collaborator another free treatment. `GUEST-` codes have `allowed_email` null until Halima has each collaborator's email; lock one with `node website-and-booking/tools/set-code-email.mjs <CODE> <email>` (`--clear` to unlock).
- **Socials.** `@haloe.health` on TikTok, Instagram and YouTube is the business account. Halima's personal `@halima.env` is separate — never conflate the two or imply they're the same account in copy.

### Functions (`functions/` maps to routes)
- `create-checkout.js` → `/create-checkout`. Creates a Stripe Checkout Session via the REST API (no SDK), embedding booking fields in `metadata[...]`. **The amount is never trusted from the client** — the request body no longer even accepts an `amount` field; the Function looks the treatment up by exact name via `findService()` (`functions/_services.js`) and computes the charge itself with that file's own `netPrice()`. An unrecognised `treatmentName` gets a 400 `unknown_treatment` rather than falling back to any client-supplied figure. For a home visit it also computes the travel fee itself from the posted postcode (`functions/_travel.js`) and adds it as a **second, separate Stripe line item** — never merged into or discounted alongside the treatment line (see Travel cost above).
- `stripe-webhook.js` → `/stripe-webhook`. Verifies the Stripe signature manually with Web Crypto (HMAC-SHA256, 5-minute timestamp tolerance), then on `checkout.session.completed` sends: a customer confirmation email, Halima's notification email (both via Resend), and a WhatsApp alert to Halima (via Twilio). The customer email **no longer links the intake form** — see the intake note under Conventions. Both emails share a **date/time-hero + grouped-card layout** built from `_email.js`'s `heroRow`/`infoCard` helpers, render in **Poppins with an Arial fallback**, and sit on the site's light cream/white/gold palette (Sep 2026 — replaced the original dark theme) with a `haloe` flower+wordmark PNG header (`images/email-logo@2x.png`, self-hosted — email clients don't reliably render SVG or load custom fonts, so the wordmark is baked into the image rather than set in Tan Ashford as text) and `color-scheme`/`supported-color-schemes` meta tags plus explicit `bgcolor` attributes throughout so Gmail/Apple Mail don't auto-invert it into a dark palette. Halima's notification shows Location as **"Clinic Day"** or **"Home visit"** (derived from `metadata[location]`, with `metadata[venue]` for clinic bookings) and postcodes are uppercased via `upperPostcode`. Both functions should pass `node --check` after editing; an unbalanced template literal in the email HTML kills confirmations silently.
- `intake-submit.js` → `/intake-submit`. Upserts the client and writes an `intake_forms` row to **Supabase (Postgres)** via its REST API (PostgREST) using the **service-role key** — which bypasses RLS, so the tables stay locked to the public anon key while this Function keeps full write access. Then emails the pre-session guide. POST only — intake data is never publicly readable. **Migrated from Cloudflare D1 (`haloe-clients`, `DB` binding) in Aug 2026;** the schema lives in `supabase-schema.sql` at the repo root (two tables, `clients` + `intake_forms`, matching the old D1 model). Needs env vars `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`.

### Slot reservation / double-booking prevention (Supabase `bookings` table)
- **Migrated from Cloudflare D1 to Supabase (Postgres) in Sep 2026** — no data carried over; the only D1 rows were Halima's own £1 live-mode tests, deleted rather than migrated. The schema lives in `supabase-bookings-schema.sql` at the repo root: `id`, `booking_date` (native `date`), `start_min`/`end_min` (minutes from midnight), `treatment`, `customer_name`/`email`/`phone`, `location` (`'clinic'|'mobile'`), `address` (clinic venue string or the client's mobile address), `amount_pence`, status `'pending'|'confirmed'`, `hold_expires_at` (unix seconds — deliberately kept as bigint, not `timestamptz`, so the existing `HOLD_SECONDS`/`Date.now()/1000` arithmetic didn't need to change). No `stripe_session_id` column this time — the D1 one was dead (defined, never populated or read).
- **D1/SQLite serializes all writes, so a plain "check-then-insert" was atomic there for free. Postgres has real concurrent writers, so it is NOT safe to run the overlap check and the insert as two separate REST calls** — two simultaneous requests could both pass the check before either commits. `reserveSlot()` in `_bookings.js` instead calls a Postgres function, `reserve_slot` (defined in the schema file, invoked via Supabase's RPC endpoint `POST /rest/v1/rpc/reserve_slot`), which takes a transaction-scoped advisory lock keyed by `booking_date` before checking for overlap — every reservation attempt for the same day is serialized, replicating D1's guarantee without serializing different days against each other. **If you ever touch `reserveSlot()`, keep the check-and-insert inside that one Postgres function — do not "simplify" it back into two REST calls from the Worker, that reopens the race.**
- `create-checkout.js` reserves the slot **before** creating the Stripe session. A win writes a `'pending'` row held for `HOLD_SECONDS` (10 min; Stripe forces its own session to live 30 min, so a payment in minutes 10–30 is still confirmed and a clash is flagged) and passes `metadata[bookingId]` + `expires_at` to Stripe. A loss (the RPC returns `null`) returns **409 `slot_taken`**, and `book.html` sends the customer back to pick another time. Stripe failure releases the hold.
- **Back from Checkout frees the hold at once (Oct 2026):** `create-checkout.js` sets Stripe's `cancel_url` to `/book.html?release=<bookingId>.<redemptionId>.<sig>` (HMAC with `STRIPE_SECRET_KEY`, `makeHoldRef()`/`parseHoldRef()` in `_bookings.js`); `book.html` POSTs it to `functions/release-hold.js` on load, which deletes the still-`pending` row and releases a still-`reserved` code, then strips the param. Forged refs do nothing; paid bookings are never touched; any failure just leaves the 10-minute hold to lapse.
- `stripe-webhook.js` flips the row to `'confirmed'` on `checkout.session.completed`. Abandoned checkouts never confirm; their holds lapse and the overlap check ignores expired pending rows, so the slot frees itself.
- **Fail-open everywhere:** if `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` aren't set or the time can't be parsed, checkout proceeds unreserved rather than blocking a paying customer.
- **Known limitations:** the homepage widget (`index.html`) takes no payment, so it neither reserves nor reflects availability — those WhatsApp bookings aren't in the database and need Halima's manual eye. Milton Hall starts must finish by the lock-up time (see the closing rule below); home visits still run to 8pm for any treatment.

### Booking → payment → notification flow (the critical path)
1. `book.html` collects selection + details into `state`, then `handlePayment()` POSTs to `/create-checkout`. Every booking is paid in full — there is no deposit type or amount to choose.
2. The function creates the Checkout Session and sets `success_url` to `booking-confirmed.html` with booking details as query params.
3. **Notification is automatic and does not depend on the customer.** Stripe calls `/stripe-webhook`, which emails Halima and the customer (and would WhatsApp Halima if Twilio were configured — it deliberately isn't). Nothing on the confirmation page is required for Halima to find out about a booking.
4. The WhatsApp alert comes from the Twilio business number, **not** the client's number — sending as the client is impossible and would be impersonation. The client's number is in the message body so Halima can reply.

### Design language (all customer-facing pages)
Reusable patterns are documented in **`COMPONENTS.md`** (repo root) — copy-paste snippets, since the site keeps CSS/JS inline per page. Update that file first when you improve one.

`book.html` and `booking-confirmed.html` share one Apple-derived language (`intake.html` left it in Oct 2026 — see its calm redesign above) — **true black, neutral greys (`#1C1C1E` surfaces, `rgba(255,255,255,0.10)` hairlines), gold used only for the active selection**, sentence-case headings with full stops, and `html { font-size: 78% }` as the single scale dial. Patterns to reuse rather than reinvent:
- **Grouped inset lists** (iOS Settings): label left, answer right, hairline between rows, 12px radius. Build them with a **`.group` wrapper that owns the card**, not per-row `:has()` adjacency rules.
- **Segmented controls** for either/or answers; **toggle switches** for consents. Use a segmented control for anything that reads as a *question* — a lone switch among questions looks out of place. Options must have **no border**; `intake.html` carries a legacy `.opt span` gold hairline that the Apple override has to reset explicitly.
- **There is no pure white in the palette.** The lightest tokens are `--cream` / `--a-t1` (`#F5F0E8`) and `--white` (`#f7f2ea`), both warm. A `#fff` toggle knob on a warm gold track reads as a foreign object — use `var(--cream)`.
- **Pill buttons** — gold fill for the primary action, neutral outline for the secondary.
- Validation sits **under the field it refers to**, with the hairline above it suppressed so field and message read as one cell.
- `book.html` drives steps from a **frosted footer**; its button proxies each step's hidden `#btn-stepN`, so the original validation still governs it.

### Privacy: the client's address
The address collected at step 3 is deliberately **kept out of the URL**. It travels to Stripe as `metadata[customerAddress]`, and reaches `booking-confirmed.html` via `sessionStorage` (`haloe_address`). Never add it to `success_url` — home addresses in URLs leak into browser history, referrer headers and server logs.

## Compliance (client-facing copy)

- **All client-facing copy must use wellness/symptom language only.** Never claim — explicitly or by implication — to **treat, cure, manage, or heal a named medical condition** (e.g. arthritis, migraine, depression, infertility, IBS, sciatica, etc.). This applies to every customer-visible string: `index.html`, `book.html`, `booking-confirmed.html`, meta descriptions, alt text, and any Stripe/WhatsApp message copy.
- Frame benefits as supporting wellbeing or easing symptoms/sensations, not as medical intervention. Prefer "may help with tension, aches, and relaxation" over "treats back pain"; prefer "supports general wellbeing" over "manages anxiety".
- When editing or adding copy, audit it against this rule before committing. If asked to add a condition-specific claim, push back and reword it into compliant symptom/wellness language.
- Claims removed in July 2026, for reference on what the rule catches: *"draws out stagnant blood, toxins, and impurities to restore the body's natural balance"* (physiological claim), *"one of the oldest and most powerful forms of natural medicine"* (calls it medicine, asserts potency), and a hero line *"addressing pain, hormonal health, fatigue"* (names conditions).

Say "CMA & IPHM accredited training" / "trained on a CMA and IPHM accredited course" — never "Halima is CMA/IPHM accredited" or `hasCredential` for the bodies themselves. ## Deployment & secrets

## Conventions & gotchas

- Keep CSS/JS inline in each HTML file — that's the established pattern. **One deliberate exception**: `services-data.js` (`SERVICES`/`PROMO_DISCOUNT`/`netPrice()`, loaded by `book.html` and `hijama-manchester.html` — `index.html`'s widget keeps its own separate `HB_SERVICES`/`HB_PROMO_DISCOUNT`, predates this file). Don't "helpfully" re-inline it back into a page — that reintroduces the exact drift/duplication it exists to prevent.
- **The custom bee cursor (`cursor.js`/`cursor.css`, plus its `cursor-bee.svg`/`cursor-bee-pointer.svg` source art) was removed entirely in Sep 2026** — every page uses the plain system cursor now. Don't reintroduce it or its `<link>`/`<script>` tags.
- **Hover styles must be guarded for touch.** On a phone `:hover` sticks to the last-tapped element. A `:hover` rule that out-specifies `.selected` (e.g. `.time-slot:hover` set gold text, `.time-slot.selected` set black) leaves the selection invisible after a tap — the picked slot rendered gold-on-gold. Wrap interactive hover states in `@media (hover: hover)` **and** add `:not(.selected)`. This bit `.time-slot` and `.cal-day` in `book.html`.
- **Autofill fields need an override or they show pale yellow.** Safari/Chrome ignore `background-color` and `color` on an autofilled field. Cover it with an inset `box-shadow` matching the field's surface plus `-webkit-text-fill-color`, and a `transition: background-color 100000s` so the yellow doesn't flash back. Present in all three forms; the inset colour differs per form (see each `:-webkit-autofill` block). On `book.html` the real step-3 fields are `.ios-row` (transparent inputs on a `#1C1C1E` card), **not** the legacy `.form-field` — match the card colour. An `.invalid` row signals with red text, so it keeps `-webkit-text-fill-color: #E5736A`.
- Design tokens are CSS custom properties redefined per file (`--gold #C8A96E`, `--black #0D0D0D`, `--cream #F5F0E8`). Reuse them rather than hard-coding colours. Font is Poppins via Google Fonts.
- **The real WhatsApp number is `447474833643`** — used everywhere. Never reintroduce the old `447700000000` placeholder.
- **The Instagram handle is `@haloe.health`.** The old `@haloe_hijama` survived in six places until July 2026 (the intake guide email, `before-your-session.html`, the homepage footer, the intake error message). Don't reintroduce it.
